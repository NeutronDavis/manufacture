# TASK: Refactor Batch Production Logging & Production Planning Engine

## Architectural Rationale & Business Justification (The "Why")

### 1. Correcting the Unit Costing Engine
In the current layout, logged batch costs display **₦0** and unit costs show blank dashes (`-`). According to the business model defined by Mr. Emeka:
* The primary objective of logging a daily batch is to calculate the **true per-unit production cost** for that specific run.
* The system must take the master recipe ingredient list, multiply ingredient quantities by live master inventory prices to get the **Total Batch Material Cost**, and divide that total by the **Actual Physical Yield** logged by the production manager:
  \\[\text{Actual Unit Production Cost} = \frac{\text{Total Batch Material Cost}}{\text{Actual Physical Yield}}\\]

### 2. Eliminating Hardcoded Bread Terminology Across Categories
Current forms use hardcoded labels like *"Flour Bags Mixed (50kg)"* and *"Loaves Produced"*, even for Water (e.g., Water 18.9L displaying "0 bags flour / 244 loaves"). 
* **Bread Line**: Baseline is 1 Bag of Flour (50 kg) \\(\rightarrow\\) Output is Loaves / Packs.
* **Water Line**: Baseline is 1 Production Run \\(\rightarrow\\) Output is Filled Dispenser Bottles / Pure Water Packs.
* **Popcorn Line**: Baseline is 1 Cooking Pot (~2 kg corn) \\(\rightarrow\\) Output is Racks / Packets.
Form labels, unit badges, and ledger columns MUST dynamically adapt based on the selected product category.

### 3. Demand-Driven Production Planning
Target production numbers should not be arbitrary guesses; they must originate from **Sales Rep Orders Placed** for the day, allowing management to compare **Requested vs. Produced** and catch supply shortfalls early.

### 4. Implementation Context (DTOs & Dummy Services)
The application currently operates without a live database, using mock data services and Data Transfer Objects (DTOs). All cost calculations, category label switches, and yield variance rules must be implemented cleanly at the DTO and mock service layer so the UI reflects live data immediately.
